# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/).

Prebuilt binaries and install instructions for each release are published on the
[GitHub Releases page](https://github.com/Akuja-Inc/taskfast-cli/releases)
(generated by [cargo-dist](https://opensource.axo.dev/cargo-dist/) on tag push);
those pages carry the download artifacts, while this file is the human-readable
record of what changed. Released tags are named `taskfast-cli-v<version>`.

## Unreleased

### Changed

- **MSRV bumped to Rust 1.97** (from 1.95). `rust-version` in `Cargo.toml`, `rust-toolchain.toml`, and the CI matrix's MSRV leg now use 1.97. Required by `progenitor` 0.17 (#248, #250). `taskfast-client` users on Rust 1.95/1.96 need to stay on the previous release.
- **`taskfast-client` is generated with progenitor 0.17 (#248, #250).** The generator API changed — `Generator::build(&settings, &spec)` + `generate_sdk()` replace `Generator::new` / `generate_tokens` — and request hooks moved from `GenerationSettings::with_post_hook` to the `progenitor_client::ClientHooks` trait. `taskfast-client` now implements `ClientHooks<()> for api::Client`, so the `x-request-id` capture (`record_corr`) still fires for every generated call (`corr_capture.rs` proves it). `MIT-0` joins the license allow list (`borrow-or-share`, a transitive of progenitor 0.17).

## [0.26.0] - 2026-11-23

### Added

- **`taskfast init` with no API key creates an unclaimed agent (Closes #238).**
  When no agent key is resolvable (flag, `TASKFAST_API_KEY`, config file) and no `--human-api-key` is given, `init` calls `POST /new` once on the configured host with no credential. The server answers with the key, a claim link and the time the key stops working; that key drives the rest of the flow and is saved together with the link and the time in `./.taskfast/config.json` (`claim_url`, `claim_expires_at`).
  The envelope reports `data.agent.action = "minted_unclaimed"` with `claim_url`, `expires_at`, `terms_url`, `terms_version` and `terms_accepted`; `--dry-run` previews it as `would_mint_unclaimed` without any request. The claim link and the deadline are printed on stderr, with the server's own Terms sentence — and only when the server says the Terms were accepted.
  A Personal API Key still wins when one is available (`--human-api-key`, or the prompt on a TTY), because that agent is claimed from the start — so at a terminal the no-key path needs `--no-interactive`.
- **Nothing that would fail later is tried after a `POST /new` success.**
  The name and description (spec length limits, and not blank after trimming, as the server checks), the wallet flags (a wallet signal; a keystore password for `--generate-wallet`) are all checked before the request, so a bad flag never spends the daily quota on an agent the run then abandons. And the claim link is announced, then the key and the link written to the config file, the moment the 201 arrives — before the rest of the flow: a later failure (a 5xx on `/agents/me`, a refused wallet registration) leaves a usable config, and re-running `init` continues from that key instead of minting another agent. A key that comes from a flag or env var instead clears a claim link that belongs to a different agent.
- **`--agent-capability` on the `POST /new` path warns instead of staying silent.** The server gives an unclaimed agent no capabilities until it is claimed, so the flag is ignored with a stderr warning; the help text says so.
- **A refused `POST /new` prints a plain message and saves nothing.**
  404 (the deployment has the route switched off) keeps the `missing_api_key` error and exit code a keyless run always had, 429 (per-address daily limit) surfaces as `rate_limited` with `retry_after_seconds`, and 503 (agent Terms not published yet) as `server` with the server's wording. The call is never retried: the server counts every request against that quota. Only the server's own 429 and 503 — a body carrying its `{error, message}` envelope — are read as those refusals; a rate limit or outage page from something in front of it keeps the generic error and is never quoted as the server's wording.
- **`taskfast-client`: `TaskFastClient::anonymous`, `TaskFastClient::create_unclaimed_agent` and `NewAgentOutcome`.**
  The first builds a client that sends no `X-API-Key`. The second wraps the generated `POST /new`, sends it exactly once, and decides the server's three documented refusals on the raw response: it returns `NewAgentOutcome::Created`, `RouteOff` (any 404), `RateLimited { retry_after }` or `NotReady { message }`, so no caller has to parse an error's `Display`; everything else is the generic `Error`.
- **`taskfast config show` redacts a `claim_url`'s `claim_token`** like `api_key` (`***<last4>`; `--reveal` prints it in full). The claim link is a bearer credential: whoever opens it and signs in becomes the agent's owner, so `config show` output must not hand the agent over.

### Changed

- **BREAKING (`taskfast-cli`): `Config` gains `claim_url` and `claim_expires_at`.** The struct is not `#[non_exhaustive]`, so an exhaustive `Config { … }` literal must add the two fields (`Config::default()` / `..Default::default()` users are unaffected). The on-disk format is backward and forward compatible: both fields are optional and older CLIs ignore them.
- **Docs: the skill's keyless path needs `--no-interactive` at a terminal, and re-run safety comes from `./.taskfast/config.json`.** SKILL.md, BOOT.md, SETUP.md and TROUBLESHOOTING.md now also say that an unclaimed agent cannot bid or accept a bid, register a webhook or update its profile until claimed (403 `claim_required`, whose remedy is the claim link, not a reactivation), that a keyless run in a directory without the saved config mints a new agent, and that `config show` redacts the claim token.

## [0.25.0] - 2026-11-22

### Changed

- **`taskfast escrow sign` opens review-clock (v3) escrows (taskfast#2044).** The escrow params request now sends `review_clock=1`. When the server returns `review_window_seconds`, the escrow is opened with `openWithReview` (selector `0xf1e32bb8`) instead of `open`/`openWithMemo`. A zero, negative or oversized window aborts before any transaction. An absent window keeps the legacy calldata. Spec: `review_clock` query parameter, `review_window_seconds`, and the `review_clock_client_required` 409 (hand-copied from server 09214d39).
- **BREAKING (`taskfast-client`):** the generated `get_bid_escrow_params` method takes a new `review_clock: Option<GetBidEscrowParamsReviewClock>` argument, and `BidEscrowParamsResponse` gains an optional `review_window_seconds` field.

### Security

- **`url` 2.5.8 -> 2.5.9 (#243).** Fixes RUSTSEC-2026-0592, a stack overflow in `Url::origin()` on nested `blob:` URLs. `Cargo.lock` only; `form_urlencoded` moves 1.2.2 -> 1.2.3 with it.

### Internal

- **Stale advisory ignores dropped (#241).** RUSTSEC-2026-0097, -0173 and -0235 are removed from `deny.toml` and the cargo-audit ignore list, and `unused-ignored-advisory = "deny"` makes a stale entry fail CI.

## [0.24.0] - 2026-11-22

### Added

- **New spec operations (client only).** The re-vendored spec adds `POST /new` (`createUnclaimedAgent`) and `GET /agents` now orders best-rated first with a `400` response for bad cursors. The generated `taskfast-client` exposes them; the CLI does not use them yet.

### Changed

- **BREAKING (`taskfast-client`): re-vendor the OpenAPI spec from server `cd36f8947286` (taskfast#2885 T11).**
  The regenerated client no longer has `ReassignTaskBody`, `ReassignTaskResponse`, `PostStakeBody`, `PostStakeBodyStakeSource`, `PostStakeResponse`, `WebhookScopedInviteReceived`, `WebhookScopedInviteReceivedData` or `OAuthAuthorizationServerMetadataAgentAuthIdentityAssertion`.
  The `direct_agent_id` field is removed from `TaskDraftPrepareRequest`, `TaskCreateRequest` and `TaskDetail`, and the abort reply status enum is narrowed to `open`.
  `BidEscrowParamsResponse` and `BidEscrowFinalizeRequest` require the poster approval fields again (see below).
- **`taskfast escrow sign` requires the server-issued `poster_approval_deadline` again.**
  The v3 optional-approval path from #213 is removed because the server no longer sends `contract_version`.

## [0.23.0] - 2026-11-20

### Removed

- **BREAKING (CLI): `taskfast post --direct-agent-id`.** The server refuses direct assignment on every public create.
- **BREAKING (CLI): `taskfast post --assignment-type`.** Open was the only accepted value; the request now sends the server default. The `would_post` dry-run envelope no longer carries `assignment_type`.
- **BREAKING (CLI): `taskfast discover --assignment-type`.** The listing has one assignment type.
- **BREAKING (CLI): `taskfast task reassign`.** Reassigning a direct-assigned task no longer exists. `task claim`, `refuse`, `reopen` and `open` stay.
- **BREAKING (CLI): `taskfast stake`.** The high-assurance tier and its performance stake are gone. `taskfast bond post` is unchanged.

### Changed

- **Replace `chrono` and `humantime` with `jiff` (Closes #235).**
  Removes both unmaintained dependencies (RUSTSEC-2026-0543, RUSTSEC-2026-0542) from the workspace.
  The generated client maps OpenAPI `date-time` fields to `jiff::Timestamp` and `date` fields to `jiff::civil::Date` via a progenitor schema conversion, with a regression test that fails if the generated code ever drifts back to `chrono`.
  `taskfast-agent::webhooks::VerifyOptions::now` is now `Option<jiff::Timestamp>`, `taskfast-client`'s `complete_artifact_upload` and `ArtifactUpload::Put::expires_at` use `jiff::Timestamp`, and the CLI's `--execution-deadline`, `payment --from/--to`, and trace timestamps move to `jiff` types.
  The six duration flags (`receipt_timeout`, `verify_timeout`) parse through jiff instead of `humantime`: the documented forms (`3min`, `90s`) and common forms (`30s`, `5m`, `1h`, `1h30m`) keep working, ISO 8601 durations (`PT90S`) are newly accepted, and negative durations are rejected. Flag types stay `std::time::Duration`, so config precedence and timeout consumers are unchanged.
  Source-breaking for `taskfast-client` (public signatures now take `jiff::Timestamp`), `taskfast-agent` (`VerifyOptions`), and `taskfast-cli` (flag value types); ships in the next minor bump. No API wire format changes.

## [0.22.0] - 2026-11-16

### Changed

- **Unify agent wallet registration and webhook provisioning orchestration (Closes #216).**
  Changes `taskfast_agent::wallet::register_wallet` return type from `Result<WalletSetupResponse>` to `Result<WalletRegistration>` to surface 409 `wallet_already_configured` conflicts structurally (source-breaking for `taskfast-agent`).
  Consolidates multi-step webhook configuration, atomic 0600 secret persistence, and event subscription replacement into `provision_webhook` shared by `taskfast init --webhook-url` and `taskfast webhook register`.
  Deprecates dead pass-through wrappers in `taskfast_agent::poster` and updates documentation on two-phase voucher task creation.

### Added

- **Map audio file extensions to MIME types for artifact uploads (Closes #199).**
  `mp3` maps to `audio/mpeg`, `wav` to `audio/wav`, `ogg` to `audio/ogg`, `m4a` to `audio/mp4`, and `flac` to `audio/flac` in `content_type_for_ext`.
  Artifact uploads with these audio extensions no longer fall through to `application/octet-stream` and trigger 415 from the server allowlist.

- **Map Office document extensions to MIME types for artifact uploads (gh#199).**
  `docx` maps to `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `xls` to `application/vnd.ms-excel`, and `xlsx` to `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` in `content_type_for_ext`.
  Artifact uploads with these extensions no longer default to `application/octet-stream` and trigger 415 from the server allowlist.

- **`taskfast fee retry <task_id>` signs and sends replacement fee payment with wallet (Closes #209).**
  `--submission-fee-voucher` is now optional. Passing it keeps the existing pass-through behavior.
  When omitted, the command reads replacement payment parameters from `GET /tasks/{task_id}/retry-fee`. It verifies that calldata matches the recipient, amount, and memo. It checks the chain ID and fee token allowlists. It signs and broadcasts the transfer using the poster keystore wallet under the per-wallet lock, then submits the transaction hash to `POST /tasks/{task_id}/retry-fee`.
  Adds `--wallet-address`, `--keystore`, `--wallet-password-file`, and `--rpc-url` flags to `fee retry`.
  If the on-chain transfer succeeds but server submission fails, the broadcast transaction hash is persisted to `StateStore`. Re-running `taskfast fee retry <task_id>` reuses the broadcast transaction hash rather than paying twice.
  `--dry-run` displays `token_address`, `recipient`, `amount`, and `memo_hash` without signing or broadcasting.

- **Deepen lifecycle event intake with unified `EventIntake` module (Closes #217).**
  Consolidates event intake across polling and streaming transports into `EventIntake` in `taskfast-cli::cmd::events::intake`.
  Encapsulates bounded `SeenIds` ring-buffer deduplication, coordinated cursor progression and seen-id commitment after successful batch processing via `StateStore`, and tolerant per-item JSON decoding.

- **Deepen `.taskfast/` local state and secret persistence into unified `StateStore` (Closes #215).**
  Consolidates `.taskfast/` local directory management into `StateStore` in `taskfast-cli`.
  Enforces atomic file creation with mode `0600` on Unix directly from creation, eliminating
  the momentary umask exposure window in `webhook register`. Automatically creates the `.taskfast/`
  directory with mode `0700` and provisions `.gitignore`. Decouples `events::seen` from `events::poll`
  path internals.

- **`escrow sign` accepts params without the approval-deadline fields (refs
  taskfast#2044).** `poster_approval_deadline` and `poster_approval_min_lifetime`
  are now optional in the spec, and `contract_version` / `review_window_seconds`
  are accepted. With both deadline fields absent and `contract_version` `"v3"`,
  the command no longer aborts: it signs no approval and finalizes without one.
  Absent fields on any other version still abort with
  `server_missing_approval_deadline`; v2 params behave as before.

- **`taskfast escalate timeout-resolve <task_id>` (Closes #211, refs
  taskfast#2044).** After the arbitrator stays silent for the contract's
  `DISPUTE_TIMEOUT` (120 days), the worker can send
  `timeoutResolveDispute(escrowId)` from their own wallet. The escrow id and
  venue contract come from `GET /tasks/{id}` (`escrow_id`, `settlement_domain`);
  escrow state, `disputedAt`, `DISPUTE_TIMEOUT` and the latest block time are read
  from the chain, so the deadline is the chain's, not the local clock's. It
  refuses, sending nothing, when the escrow is not `Disputed`, when the deadline
  has not passed, or on a chain id mismatch. The transaction hash is a hint only;
  the CLI writes nothing to the server and does not predict who is paid.
  `--dry-run` makes read-only RPC calls and sends nothing.
- **`taskfast escalate reject-remedy <task_id>` and `escalate sign <task_id>`
  (Part of taskfast#2044).** A poster can reject a failed remedy, then sign and
  send `dispute(escrowId)` from their own wallet, with every value taken from
  `GET /tasks/{id}/dispute/signing-params`. `sign` refuses before any
  transaction when the keystore differs from the escrow's `poster_wallet_address`,
  when `chain_id` differs from the configured network or the RPC node, or when
  the escrow contract is malformed or zero. A `lapse_pending` response warns and
  still sends. Output says "submitted": the dispute counts once the server
  observes the finalized `EscrowDisputed` log. The server's 409/503 refusals keep
  their codes and gain a one-line hint. `taskfast-agent` gains
  `TaskEscrow::disputeCall`.
- **`taskfast fee retry <task_id> --submission-fee-voucher <0x...>`.** Retries a
  failed submission-fee charge. The server now requires the poster's freshly
  signed fee transfer (or the hash of one already broadcast) in the request
  body; the flag is passed through unchanged. The CLI signs and sends nothing.

### Changed

- **Deepen Tempo wallet signing and RPC broadcast session behind unified interface (gh#214).**
  Introduced `TempoSession` in `taskfast-cli` which encapsulates keystore path resolution, password unlocking, address validation, RPC connection, automatic wallet locking, and receipt polling. Migrated `escrow`, `bond`, `escalate`, `cast`, and `post` to the unified session, eliminating duplicate ERC-20 preflight logic (`balanceOf`, `allowance`, `approve`). Migrated `settle` keystore loading and preflight address validation to `wallet_args::load_signer_and_validate`. Added an in-process `MockTempoRpc` backend for hermetic testing. Unified `resolve_wallet_password` in `init` with `wallet_args::resolve_password_with_inline` to enforce `Zeroizing<String>` memory safety and reject interior newlines.

- **`task retry-fee <id>` is now a redirect and makes no request.** Since
  2026-11-01 the server refuses a retry without the poster's fresh voucher, and
  adding the flag here would break the library API without a version bump, so
  the command prints a usage error naming `taskfast fee retry`. Moving the flag
  back under `task` needs the next minor release.

- **Re-vendored the OpenAPI spec** (fetched 2026-11-09). Adds operations
  `getDisputeSigningParams`, `rejectRemedy`, `triggerReviewTimeout`.

### Fixed

- **Acquire exclusive wallet lock on all mutating broadcasts and receipt polling (gh#214).**
  Fixes a concurrency bug where `escrow sign`, `bond post`, `escalate sign`, `escalate timeout-resolve`, and `cast send` broadcast transactions without acquiring `wallet_lock`. All mutating transactions and receipt polling now serialize under `TempoSession`'s exclusive wallet lock.

- **`events stream` and `events poll` drop duplicate events (gh#204).**
  The newest 10,000 `event_id`s are kept in `events.seen` next to the config
  and survive restarts. `stream` still acks a duplicate so the server moves on
  but prints nothing; `poll` skips it. If the file cannot be read or written,
  the CLI warns once on stderr and keeps printing events.

## [0.20.1] - 2026-10-18

### Fixed

- **Artifact uploads to R2 no longer fail with HTTP 400 (gh#193).** 0.20.0
  sent `Content-Length` twice on the presigned PUT: once from the file size
  and once from the server's signed headers. R2's edge refuses a duplicate,
  so every `task submit --artifact`, `task remedy --artifact` and
  `artifact upload` on staging and production failed with
  `artifact storage PUT failed: HTTP 400`. The PUT now sends one
  `Content-Length`, set from the file size.

## [0.20.0] - 2026-10-17

### Changed

- **Artifacts upload straight to R2, never through the app on staging or
  production (gh#193).** `task submit --artifact`, `task remedy --artifact`
  and `artifact upload` now ask the server for a presigned PUT
  (`POST /tasks/{id}/artifacts/uploads`), stream the file to it with an
  explicit `Content-Length`, then record it with
  `POST /tasks/{id}/artifacts/uploads/{upload_id}/complete`. The PUT uses a
  separate HTTP client without the API key and with redirects off, and only
  goes to `https://*.r2.cloudflarestorage.com` (`--allow-custom-endpoints`
  lifts that pin). PUT transport errors drop the presigned URL, so upload
  credentials never reach CLI output or agent logs. Complete retries 503,
  timeouts and dropped response bodies until the upload expires, and never
  re-sends the bytes. Multipart through the app is now a
  `--env local` fallback only; on staging and production a server without
  direct uploads fails with `server: this server does not offer direct
  uploads`. The server still owns the size limit: an oversize file fails at
  initiate with `validation [file_too_large]` and the server's `max_bytes`.
  Needs taskfast#1690 on the server.

### Fixed

- **Skill escrow recovery no longer recommends blind retries (gh#196).**
  A fresh `escrow sign` invocation can fund a second escrow after an
  ambiguous transaction result or failed finalize request. The skill now
  requires inspecting the original transaction and recovering its voucher,
  or stopping for operator intervention; a pending bid or 409 alone does
  not prove retry safety or success. Both shipped skill copies are updated;
  escrow runtime behavior is unchanged.
- **`task reopen --help` described stale semantics.** The text claimed the
  command flips a direct-assigned task back to `assigned`; `reopen` POSTs
  `/tasks/{id}/reopen`, which reopens an `abandoned` task for rebidding
  (back to `open`, per the API spec). Help text corrected; behavior
  unchanged.

### Docs

- **Bundled `taskfast-agent` skill realigned with the CLI surface.** All six
  skill files audited against the 0.19.8 command tree and the vendored API
  spec; fixes include required `post` flags in examples, `message send
  --content`, `config show` (not `config get`), tiered completion fees
  (2.5% default `open` tier / 10% `high_assurance`) replacing the flat 10%
  claim, `taskfast settle` documented as implemented (poster EIP-712
  settlement), escrow signing documented as non-idempotent with explicit
  transaction-recovery guidance, poster payment verification via the
  task-detail `settlement` block (`payment get` is worker-only), corrected
  exit-code/jq-path/webhook-path
  references, and the never-emitted `pickup_deadline_warning` marked
  deprecated. The vendored copy under `crates/taskfast-cli/skills/` is
  re-synced byte-identically.

## [0.19.4] - 2026-10-11

### Fixed

- **A response field the CLI doesn't read can go missing without breaking
  commands** (gh#178). The codegen normalizer now drops `required` from
  response properties except a `KEEP_REQUIRED` list of the fields the CLI
  reads as plain values (escrow, stake, draft-signing, settlement-domain,
  readiness, webhook and artifact fields, the event-page envelope and event
  identity). Every other response field is now `Option`, so a server that
  removes it, or stops always sending it, no longer fails decode in released

  untouched.

- **`taskfast-client` is bumped to 0.15.0** because generated response fields
  outside `KEEP_REQUIRED` change from `T` to `Option<T>` (cargo-semver-checks
  doesn't inspect field types, so this bump is manual). **`taskfast-codegen` is
  bumped to 0.3.0** because `Report` gains `response_required_relaxed`.

## [0.19.0] - 2026-10-10

### Fixed

- **`taskfast events stream` no longer stalls on its first event** (gh#169).

### Changed

- **`taskfast bond post` reads the task-bond contract address from the
  server's `GET /config/network` (`task_bond_contract`).** `--task-bond` is

  edit; an out-of-contract value is a normal usage error instead of a latent

  less than the server's `poster_approval_min_lifetime` remaining, and a

### Security

- **F1 PathUSD fee-token allowlist.** `taskfast post` now fetches
  `eth_chainId` from the configured RPC and refuses to sign if the
  server-returned `token_address` isn't PathUSD on that chain (or any
  token on anvil/hardhat locals). Shields against a compromised API
  redirecting the ERC-20 submission-fee transfer. An audit line is
  emitted to stderr on every sign.
- **F3 atomic webhook-secret write.** `webhook register --secret-file`
  now writes to a sibling `.tmp`, chmods it `0600`, then renames into
  place — closing the brief `0644` window a concurrent reader on a
  shared host could observe.
- **F4 tight `.taskfast/` parent-dir perms.** `Config::save` now chmods
  the parent directory to `0700` on unix so `.taskfast/` itself is no
  longer world-listable after `taskfast init`.
- **Keystore + config written `0600` at creation time (gh#78).** Both the
  wallet keystore and `.taskfast/config.json` are now created with mode
  `0600` from the first `open` instead of inheriting the umask and being
  chmod'd afterward — closing the window where the encrypted private key /
  `api_key` was briefly `0o666 & ~umask` (e.g. `0664` under `umask 002`) and
  world-readable. `load_signer` also warns when an existing keystore is
  group/world-accessible. Additionally, `Config::save` drops a `.gitignore`
  of `*` into `.taskfast/` so the plaintext `api_key` can't be committed by
  accident from inside a git repo (existing `.gitignore` left untouched).
- **F5 no HTTP redirects.** The typed client pins
  `reqwest::redirect::Policy::none()`. `X-API-Key` is a custom header
  (not `Authorization`) and would otherwise be replayed verbatim on a
  cross-host 3xx — the real API never 3xx's, so refusing all redirects
  is safe and turns a malicious `Location` into an immediate failure.
- **F6 error-variant-only retry logs.** `taskfast_agent::retry`
  no longer logs the raw `Error` `Display` at `debug` level — only the
  stable variant tag via `Error::kind()`. Prevents a server that echoes
  request bodies into its error strings from paging an `X-API-Key`
  value into every log sink.
- **F7 zeroized wallet passwords.** `resolve_password` returns
  `zeroize::Zeroizing<String>`; the CLI's plaintext-password buffer is
  scrubbed on scope exit. The `alloy-signer-local` internal copy is
  outside our control — this shrinks the window + scope inside our
  own address space.
- **F8 response-body size cap.** Hand-rolled client read paths
  (`get_user_profile`, `upload_artifact`, `classify_response`) stream
  via `chunk()` with an explicit ceiling — 16 MiB for success bodies,
  64 KiB for error envelopes. A compromised or buggy server can no
  longer memory-exhaust the CLI with a gigabyte response.
- **F9 wallet sign+broadcast file-lock.** `taskfast post` acquires an
  exclusive OS-level lock on `<keystore-dir>/.taskfast-wallet.lock`
  across `eth_getTransactionCount` → `eth_sendRawTransaction`.
  Concurrent invocations against the same keystore on one host can no
  longer collide on nonce; distinct wallets still proceed in parallel.
- **F10 Docker non-root.** The published image now creates a
  `taskfast` user (uid 1000) and `USER taskfast:taskfast`s before the
  entrypoint. Default bind-mount writes land as uid 1000, and a
  compromised binary can no longer chmod its own copy on tight host
  ACLs.
- **F11 cosign keyless-signed releases.** Release workflow aggregates
  per-archive `.sha256` files into a single `SHA256SUMS`, signs it via
  Sigstore Fulcio using the GitHub Actions OIDC workflow identity, and
  uploads `SHA256SUMS.sig` + `SHA256SUMS.pem` to the GitHub Release.
  Verifiers: see `SECURITY.md` Operator Guidance for the
  `cosign verify-blob` incantation.
- **F12 wiki-sync dedicated deploy key.** Wiki mirror workflow
  authenticates via a dedicated SSH deploy key (`WIKI_DEPLOY_KEY`
  secret) instead of the broad `GITHUB_TOKEN`, and `permissions:` is
  narrowed to `contents: read`. Operator one-time setup is documented
  in the workflow header.
- **F13 reject multi-line password files.** `resolve_password` now
  refuses a password file containing an interior `\n` or `\r` (a
  trailing newline is still fine). Prevents a file with a commented
  header or two concatenated passwords from being silently accepted as
  the first line.
- **F15 security_warnings[] envelope field.** Every JSON envelope now
  carries a `security_warnings` array (empty on healthy runs). Current
  signals: `custom_endpoints_allowed` when `--allow-custom-endpoints`
  is active; `password_env_var` when `TASKFAST_WALLET_PASSWORD` is set.
  Orchestrators can `.jq '.security_warnings | length > 0'` to gate.
- **Operator Guidance** added to `SECURITY.md` — install verification,
  secrets hygiene, wallet safety, network, webhook, supply chain, and
  incident-response playbooks.

- **`taskfast task`** (`approve`/`dispute`/`cancel`/`submit`) — multipart artifact
  upload and completion.
- **`taskfast settle`** — EIP-712 `DistributionApproval` settlement.
- **`taskfast events poll`** and headless agent mint via `--human-api-key`.
- **`taskfast webhook`** subcommand and `init` webhook/faucet setup.
- Typed API client (`taskfast-client`) with X-API-Key auth and structured error
  mapping (401/403 → auth, 422 → validation, 429 → rate-limited w/ Retry-After,
  5xx → retried server error), plus agent utilities (backoff retry, wei decoding,
  event polling).
- Production `Dockerfile`, README, and the cargo-dist release pipeline.
